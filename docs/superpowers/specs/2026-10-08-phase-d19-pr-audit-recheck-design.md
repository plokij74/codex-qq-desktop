# Phase D19：修复后复审与问题追踪

日期：2026-10-08。状态：设计已确认，实现与本地验收完成。实际结果及环境限制见 [实施记录](../plans/2026-10-08-phase-d19-pr-audit-recheck.md)；真实 GitHub.com/Enterprise 验收仍需指定测试仓库。

## 目标与已确认决策

在 D18 更新 PR 并核对成功后，用户手动发起只读复审，逐项判断该次修复选择的 1–5 个原问题是否解决。允许检查包含修复提交的最新 PR head；每次结论绑定实际检查的提交，独立保存。

- 入口限定为 D18 成功交付后的手动操作，不自动调用模型。
- 一次检查该修复的全部原始问题，不重新选择，不同时开展完整 PR 审查。
- 只保留 AI 结论，不增加人工修改、人工确认或驳回记录。
- 对仍存在或无法判断的问题，提供再次复审与完整 AI 审查入口；后续修复继续从新的 D17 报告发起。
- 不直接再次生成修复，不发布 Review、回复或解决线程，不执行测试或自动合并。
- 沿用当前 API/模型配置、gh 登录、origin 同仓库的 OPEN PR（含 Draft）及 GitHub.com/Enterprise。

## 用户流程与结论

1. D18 更新结果卡、修复历史和 PR AI 审查区域提供“复审本次修复”。
2. 运行时展示原报告、修复提交、目标提交和进度。目标包含后续提交时明确提示“包含后续改动”。
3. 结果按原报告顺序显示原问题、AI 结论、理由及可展开的固定提交代码依据。
4. 默认显示最近完成的一次复审；进行中的任务、失败尝试和其他历史另行显示。每次重试生成新记录，原报告及旧结论不覆盖。
5. 提供“再次复审”“完整 AI 审查”“返回原发现”。静态复审不能代替测试结果、人工确认或合并条件。

| 结论 | 要求 |
| --- | --- |
| AI 判断已解决 | 说明原触发条件如何消除，并提供目标提交中的依据 |
| AI 判断仍存在 | 说明当前触发条件，并提供目标提交代码位置 |
| 无法判断 | 说明缺少的证据或读取限制，不推断问题已解决 |

局部刷新保留 D17/D18 草稿、焦点和滚动。异步请求按绑定、页面及请求代次隔离；旧响应不能启动新任务或覆盖当前内容。历史结论在重新核实前不显示为当前有效。

## 来源、固定提交与证据

新增独立 PrAuditRecheckManager 和复审 runtime，复用 D17 模型调用及固定提交读取能力。

主进程通过可信 worktree marker 解析 resultId → auditRepairRef → auditRef → findingIds。只接受 pr_updated 或已确认交付的 pr_update_cleanup_pending；pr_update_uncertain 必须先完成现有只读核对，不因暂时看到某个远端 head 而推定成功。

校验原报告内容、修复来源、单父提交和 tree 身份。D18 交付使原报告 stale 属于正常历史变化：历史来源校验仅忽略这一标志，仍验证保存的原始 repairRevision。不得调用要求报告新鲜的 D18 修复选择逻辑，也不得放宽 D18 新修复的资格检查。

保持同一规范项目范围、origin 仓库、PR 及 base/head 分支；PR 必须仍为 OPEN，允许 Draft。当前 head 必须等于修复提交或以它为祖先。强推移除修复提交、对象缺失或祖先关系无法证明时拒绝启动。后续提交即使撤销了修复，仍应检查其实际代码并可判为问题仍存在。

每次冻结当前 head/base SHA、merge-base 和描述指纹；允许它们相对原审查发生变化。准备结束和调用模型前复检，完成后再次检查：运行期间来源变化时保留结果但标记 stale；查询失败时标记 unknown（当前状态未核实）。查看历史不要求 PR 仍打开，但新任务必须满足资格。

拆分固定提交读取和 D17 完整 PR diff 校验。D19 读取原问题所在提交、修复提交和目标提交，提供有界的“原 head → 修复提交”“修复提交 → 目标 head”差异。修复后 PR 没有文本 diff 也可复审。

- 原 LEFT 读取原 merge-base 下的 contextPath，原 RIGHT 读取原 head。
- 使用固定提交差异、重命名信息及目标代码搜索重新定位；新依据不要求落在当前 PR diff 内。
- 文件删除、行号移动或搜索无结果本身不能证明已解决；模型必须解释原触发条件如何消除。
- 模型只能引用本次实际读取所产生的证据标识。代码证据由主进程绑定到提交、路径和行范围；缺失路径证据也由主进程核对。
- resolved/still_present 必须引用目标提交依据；still_present 必须是代码依据。resolved 使用路径缺失证据时还须确认该路径原先存在，解释功能或调用关系为何消除了问题。
- 范围外、符号链接、子模块、二进制或读取受限内容不能作为已读取代码证据。证据不足使用 unknown；系统级快照不完整则任务失败。

临时引用使用 refs/codex/pr-audit-recheck/<recheckRef>/base|head 命名空间。finally 清理；绑定项目时只清理本模块无活动所有者的遗留引用。不改变工作区、index、远端跟踪分支或 FETCH_HEAD；脏工作区允许发起只读复审。

## 运行、接口与存储

D17/D19 共用每规范项目一个、全局两个活动审查的配额。沿用 D17 的八轮、五分钟、单文件 128 KiB、差异 256 KiB、累计上下文 512 KiB 和模型上下文预算。输入的原问题不截断后继续；仅开放固定提交读取、列举、搜索和提交结论工具。

切换页面、会话或最小化后继续执行；解绑、项目删除、sender 销毁或退出取消任务。取消信号保留至后台任务结束。重启把活动任务标记 interrupted，手动重试创建新记录；不恢复模型调用。

所有 IPC 都要求 sender 所属的 projectBindingId；复审仅由 UI 启动，不新增聊天 Agent 工具。

| IPC 前缀 engineering:pr-audit:recheck: | 额外输入 | 输出 |
| --- | --- | --- |
| start | resultId | recheckRef、存储状态 |
| list | 可选 prNumber | 可复审交付条目、复审历史、存储状态 |
| get | recheckRef | 复审记录、原问题、新鲜度及来源可用性 |
| cancel | recheckRef | 取消请求结果 |
| context | recheckRef、evidenceId | 固定提交代码片段或已核实路径缺失 |

recheckRef 使用 pac_<24 hex>；证据标识使用 pce_<24 hex>。事件 engineering:pr-audit:recheck:event 仅发送 ref、项目 key、PR、状态和轮次给当前所有者，不携带问题正文或代码。Renderer 不提交仓库路径、SHA、原问题正文、证据位置或结论。

结构化模型输出为 summary 和 findings，每项包含 findingId、status（resolved/still_present/unknown）、reason、evidence 标识列表。所选 ID 必须完整且不重复，证据必须属于本次读取。非法报告允许一次纠正，仍无效则失败。

engineering-pr-audit-rechecks.json v1 使用 safeStorage 加密，保存来源关联、交付身份、目标快照、结论、证据位置、时间和数值用量。代码片段按需读取，不保存完整提示和工具轨迹。每项目最多 50 条、全局 200 条，淘汰最旧非活动记录。

保留的复审记录保护其 D18 来源及 D17 原报告；恢复这些引用后才进行来源淘汰。扫描失败保守保留，不能淘汰时拒绝新增。临时写入、解密回读校验后 rename；加密或写入失败退化为内存并提示，损坏文件保留。

现有 D17 报告、repair store 和 v4 marker 格式保持兼容。已有 D18 成功结果经主进程校验后可复审；缺少来源时显示原因。结论、代码及提示不进入聊天、localStorage、导出、记忆或 Hooks；usage 仅记录数值。

## 验收

- fake model/GitHub：三类结论、多问题完整性、非法证据、原始发现与发布草稿隔离、预算、次数、取消、来源变化及无自动后续动作。
- 真实临时 Git：精确修复提交、后续提交、修复被撤销、强推、LEFT/RIGHT、删除/重命名、空 diff、子目录、符号链接/子模块、脏工作区、临时引用清理。
- IPC/存储：跨 sender/项目、参数注入、共享配额、迟到响应、加密降级、损坏、容量与引用保护、重启恢复及已有 D18 结果。
- 真实 Electron 离线冒烟：1100×720 与 900×580，交付后复审、证据查看、历史、重新加载、过期提示与完整审查入口；回归 D17/D18。
- 针对性测试、完整 npm test、修改脚本 node --check、git diff --check 通过。

设计前已运行 D17 state/runtime 与 D18 store/manager 的 27 项基线测试，全部通过。这些结果不是 D19 新能力验收。真实 GitHub.com/Enterprise 环境仍需指定测试仓库独立验收；离线脚本不执行真实远端写入。
